# PoC 1 Heuristic Visualizations

Generated by `npupy_xdna/scripts/generate_poc1_plots.py` from Wave-2 characterization JSONL data.

---

## 01_gemm_throughput.png

**What it shows:** GOPS vs matrix dimension M (=K=N) for `gemm_fusion`, grouped by epilogue (`none` vs `relu`).  
**Key takeaway:** Peak throughput of **5159 GOPS** is reached at 2048³. Performance degrades at 4096³ due to off-chip memory pressure. The `relu` epilogue adds ~10–15% overhead at small sizes but converges at large sizes.

---

## 02_gemm_npu_vs_cpu_latency.png

**What it shows:** NPU vs CPU median latency (µs) across GEMM sizes (epilogue=none). NPU covers all 5 measured sizes; CPU only goes to 1024³ (larger sizes were skipped as impractically slow).  
**Key takeaway:** NPU dominates at every measured size — 15× faster at 256³, rising to 471× at 1024³. No crossover is observed within the tested range: NPU latency stays sub-linear while CPU scales cubically.

---

## 03_bandwidth_scaling.png

**What it shows:** Effective bandwidth (GB/s) vs element count for `col_independent` and `compute_pool` templates, both on log₂ scale.  
**Key takeaway:** `col_independent` scales cleanly from 0.2 GB/s at 16K elements to **10.8 GB/s** at 1M elements, approaching the NPU2 memory bandwidth ceiling. `compute_pool` is capped by a ~15 ms dispatch floor (hardware design issue), yielding only 0.55 GB/s even at 2M elements — a clear negative result.

---

## 04_template_decision_map.png

**What it shows:** 2D heatmap with operation type on the Y-axis and shape size on the X-axis. Each cell shows which template the `RegionClassifier` selects (or `cpu_fallback` if no rule matches).  
**Key takeaway:** Only `matmul`/`matmul_fused` operations at the 5 supported GEMM sizes get assigned `gemm_fusion`. Elementwise ops at large sizes are assigned `col_independent` or `compute_pool` per rules.yaml priority. `chained_elementwise` maps only to `cgra` (256 elements). Most (op_type, size) combinations have no matching template and fall back to CPU.

---

## 05_offload_decision_map.png

**What it shows:** Same 2D grid as plot 4, but colored by the `OffloadHeuristic` decision: green = offload to NPU, red = cpu_fallback.  
**Key takeaway:** Only `matmul` at the 5 GEMM sizes is dispatched to the NPU. All elementwise templates (col_indep, compute_pool, cgra) are rejected by the offload heuristic because CPU is faster than NPU for all currently measured sizes — the dispatch overhead exceeds the compute savings.

---

## 06_all_templates_latency.png

**What it shows:** Grouped bar chart (log scale) comparing NPU and CPU median latency for each template at its peak-throughput size: gemm_fusion@2048³, col_indep@1M, compute_pool@2M, cgra@256.  
**Key takeaway:** `gemm_fusion` is the only template where NPU clearly wins (CPU latency estimated >1 s at this size). For all elementwise templates, CPU latency is 1–3 orders of magnitude lower than NPU, confirming that the 300–15000 µs dispatch floors make NPU offload uneconomical for small-to-medium elementwise workloads.

## 09_cgra_chain_depth.png

**What it shows:** Two panels: (left) per-op latency (µs) vs CGRA chain depth (3/8/16 ops); (right) total NPU vs CPU latency vs chain depth.  
**Key takeaway:** Per-op cost drops from 80 µs at depth-3 to 23 µs at depth-16, showing amortization of the ~240 µs dispatch floor. However, CPU remains faster at all depths — the NPU only becomes competitive beyond ~30+ chained ops, outside the current test range. Data source: `cgra_depth_sweep.jsonl`.

## 10_tile_size_sweep.png

**What it shows:** Two panels: (left) derived GOPS per tile config; (right) NPU median latency (ms) per tile config, for 2048³ GEMM.  
**Key takeaway:** Tile [64×64×64] delivers 4878 GOPS vs only 1743 GOPS for [32×32×32] — a 2.8× improvement. The [128×64×128] config failed to compile (aiecc error), confirming that not all tile shapes are supported by the AIE2P toolchain. Data source: `gemm_tile_sweep.jsonl`.

## 11_compile_cache_stats.png

**What it shows:** Two panels: (left) cold vs warm compile load time (ms, log scale) per template; (right) cold/warm speedup ratio per template.  
**Key takeaway:** `gemm_fusion` cold load takes 115 ms (xclbin synthesis) vs 0.047 ms warm — a **2479× speedup** from caching. Elementwise templates (col_indep, compute_pool, cgra) have negligible cold-load times (<0.05 ms) since they use pre-compiled bitstreams. The cache is critical for workloads that change templates frequently. Data source: `compile_cache.jsonl`.

## 12_arithmetic_intensity.png

**What it shows:** Effective bandwidth (GB/s) vs element count (log₂ scale) for `col_indep` (elementwise/relu) and `tanh` (via col_indep template). `hash.jsonl` was not collected (benchmark skipped).  
**Key takeaway:** Both workloads scale similarly — bandwidth grows from <1 GB/s at 64K elements to 6–23 GB/s at 4M elements. `col_indep` peaks at 23 GB/s (4M elements) while `tanh` peaks at 6 GB/s (4M), reflecting the higher arithmetic cost of transcendental ops. Data sources: `col_indep.jsonl`, `tanh.jsonl`.

## 13_col_indep_extended.png

**What it shows:** Two panels: (left) bandwidth (GB/s) vs size extended to 4M elements, with V1 (≤1M) and V2 (2M, 4M) points highlighted; (right) NPU/CPU speedup ratio vs size.  
**Key takeaway:** The V2 extension reveals the NPU crossover point: `col_indep` achieves NPU=CPU parity at ~2M elements (speedup 1.12×) and NPU wins by 1.65× at 4M elements (23.3 GB/s). This changes the offload heuristic threshold from "never" to "≥2M elements". Data source: `col_indep.jsonl`.

## 14_compute_pool_8core.png

**What it shows:** Two panels: (left) bandwidth (GB/s) vs size for 8-core vs 32-core compute_pool; (right) NPU median latency (ms) vs size.  
**Key takeaway:** The 8-core pool shows a ~7.5–8 ms dispatch floor vs ~15 ms for the 32-core pool — roughly 2× improvement. Despite lower floor, peak bandwidth for 8-core (1.15 GB/s at 2M elements) still lags far behind col_indep (23 GB/s), confirming the compute_pool template architecture is fundamentally limited by dispatch overhead regardless of core count. Data sources: `compute_pool_8core.jsonl`, `compute_pool.jsonl`.
