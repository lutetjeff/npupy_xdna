# PoC 1 Heuristic Visualizations

Generated by `npupy_xdna/scripts/generate_poc1_plots.py` from Wave-2 characterization JSONL data.

---

## 01_gemm_throughput.png

**What it shows:** GOPS vs matrix dimension M (=K=N) for `gemm_fusion`, grouped by epilogue (`none` vs `relu`).  
**Key takeaway:** Peak throughput of **5159 GOPS** is reached at 2048³. Performance degrades at 4096³ due to off-chip memory pressure. The `relu` epilogue adds ~10–15% overhead at small sizes but converges at large sizes.

---

## 02_gemm_npu_vs_cpu_latency.png

**What it shows:** NPU vs CPU median latency (µs) across GEMM sizes (epilogue=none). NPU covers all 5 measured sizes; CPU only goes to 1024³ (larger sizes were skipped as impractically slow).  
**Key takeaway:** NPU dominates at every measured size — 15× faster at 256³, rising to 471× at 1024³. No crossover is observed within the tested range: NPU latency stays sub-linear while CPU scales cubically.

---

## 03_bandwidth_scaling.png

**What it shows:** Effective bandwidth (GB/s) vs element count for `col_independent` and `compute_pool` templates, both on log₂ scale.  
**Key takeaway:** `col_independent` scales cleanly from 0.2 GB/s at 16K elements to **10.8 GB/s** at 1M elements, approaching the NPU2 memory bandwidth ceiling. `compute_pool` is capped by a ~15 ms dispatch floor (hardware design issue), yielding only 0.55 GB/s even at 2M elements — a clear negative result.

## 04_template_decision_map.png

**What it shows:** 2D heatmap with operation type on the Y-axis and shape size on the X-axis. Each cell shows which template the `RegionClassifier` selects (or `cpu_fallback` if no rule matches).  
**Key takeaway:** Only `matmul`/`matmul_fused` operations at the 5 supported GEMM sizes get assigned `gemm_fusion`. Elementwise ops at large sizes are assigned `col_independent` or `compute_pool` per rules.yaml priority. `chained_elementwise` maps only to `cgra` (256 elements). Most (op_type, size) combinations have no matching template and fall back to CPU.

---

## 05_offload_decision_map.png

**What it shows:** Same 2D grid as plot 4, but colored by the `OffloadHeuristic` decision: green = offload to NPU, red = cpu_fallback.  
**Key takeaway:** Only `matmul` at the 5 GEMM sizes is dispatched to the NPU. All elementwise templates (col_indep, compute_pool, cgra) are rejected by the offload heuristic because CPU is faster than NPU for all currently measured sizes — the dispatch overhead exceeds the compute savings.

---

## 06_all_templates_latency.png

**What it shows:** Grouped bar chart (log scale) comparing NPU and CPU median latency for each template at its peak-throughput size: gemm_fusion@2048³, col_indep@1M, compute_pool@2M, cgra@256.  
**Key takeaway:** `gemm_fusion` is the only template where NPU clearly wins (CPU latency estimated >1 s at this size). For all elementwise templates, CPU latency is 1–3 orders of magnitude lower than NPU, confirming that the 300–15000 µs dispatch floors make NPU offload uneconomical for small-to-medium elementwise workloads.
